# 개선 우선순위와 순차 실행 계획

> OKF 종류: `plan` · 상태: `proposed` · 기준일: 2026-10-05

## 목적과 범위

현재 구현과 역할별 검토를 근거로 다음 개선 순서, 담당 세션, 완료 조건을 정한다. 메인이 검토 결과를 통합하며 기존 역할별 세션 하나씩 실행한다. 이 문서는 구현 완료나 운영 검증 통과를 의미하지 않는다.

기준 코드는 `main`의 `1bd1dfa`다. 역할별 작업 폴더에는 이전 변경이 남아 있을 수 있으므로 현재 원본 저장소를 검토 기준으로 사용한다. 새 의존성, 주문 기능, 운영 재배포와 실제 수집·전송은 계획 수립 범위에 포함하지 않는다.

## 현재 확인한 사실

- 10월 3일 scheduler 설정 파일 누락을 해소한 후 삼성전자·SK하이닉스 수집 성공 2건, 실패 0건과 web·DB 실행을 확인했다. 두 종목의 가격·날짜별 수급 기준일은 10월 2일이었다. 이는 해당 시점의 확인이며 10월 5일 운영 상태를 보증하지 않는다.
- 같은 시점 지표·신호·리포트는 이전 기준일이었다. [스케줄러](../../src/invest_bot/jobs/scheduled_collection.py)는 원본 수집을 실행하며 분석·리포트 생성과는 별도다.
- 디자이너는 10월 3일 8개 메뉴와 주요 데스크톱·390px 화면을 검토했고, 10월 5일 홈·리포트를 재확인했다. 수급 없음 안내, 오래된 판단 안내, 어두운 신호 글자, 외부 전송 안내, 소개·카드의 강조, 백테스트 데이터 기간, 모바일 차트 배치를 개선 후보로 제시했다.
- 수급 관측일과 값은 `investor_daily_summary`에 있고 `investor_daily`에는 날짜 없는 가격 요약이 저장된 운영 사례를 확인했다. 따라서 summary를 사용한다는 이유만으로 잘못된 경로라고 판단하지 않는다. [수급 응답 변환](../../src/invest_bot/market/domestic_stock.py)과 [리포트 생성](../../src/invest_bot/jobs/generate_market_report.py)을 함께 확인한다.
- 10월 5일 운영 PostgreSQL에서 읽기 전용 트랜잭션으로 현재 정렬과 날짜 있는 record 우선 정렬을 비교했다. 현재 `as_of_date DESC`는 삼성전자 6월 28일·SK하이닉스 8월 17일의 기준일 NULL·0행 snapshot을 선택했다. `DESC NULLS LAST`는 두 종목의 10월 2일·30행 수급 snapshot을 선택했다. 최신 수급 없음 안내의 구체적인 조회 원인을 확인했으며 데이터는 변경하지 않았다.

## 우선순위 판단 기준

1. 잘못된 기준일·누락 표시·미래 데이터 사용처럼 판단을 바꾸는 정확성 문제를 먼저 해결한다.
2. 실행이 어떤 데이터를 바꾸고 외부로 무엇을 전송하는지 명확히 한다.
3. 시작·실패·재시작을 검증할 수 있게 하고 실제 실행과 문서 상태를 일치시킨다.
4. 기존 [디자인 계약](../../DESIGN.md)과 컴포넌트를 사용해 정보 위계·대비·배치를 개선한다.
5. 증거가 부족한 신규 기능보다 작은 재현과 회귀로 확인할 수 있는 변경을 우선한다.

## 역할별 작업 문서

다섯 역할의 검토는 모두 완료됐다. 작업별 상세 조건·상태는 아래 문서에서 관리하고, 전체 우선순위와 추천 순서는 [개선 작업 색인](improvements/README.md)을 따른다. 이 계획은 검토 배경과 진행 원칙을 유지하며 상세 작업을 중복 관리하지 않는다.

| 담당 세션 | 작업 문서 | 선정된 작업 |
| --- | --- | --- |
| 데이터 수집·저장 개선 | [데이터](improvements/data.md) | 최신 NULL 정렬·숫자형 날짜·수집 범위 |
| 퀀트·백테스트·리포트 개선 | [퀀트](improvements/quant.md) | 중복 거래일·저장 신호 정합성·조합 재현 설정 |
| 대시보드 구조·조회 개선 | [대시보드](improvements/dashboard.md) | 수급 연결·기준일 안내·전송 안내·대비·배치·입력 범위·모바일 차트 |

## 순서의 근거

첫 단위는 [G01a 최신 snapshot 정렬](improvements/data.md#g01a)이다. 운영에서 확인한 잘못된 표시의 직접 원인을 수정하고 QA01의 양쪽 DB 회귀를 완료한 뒤 다음 작업으로 이동한다. 숫자형 날짜는 G01b의 별도 P2 단위다.

다음 P1은 재시작 실패 처리(G02), 중복 거래일(G03), 저장 신호 정합성(G04), 수급 연결·상태 안내(G05a·G05b)다. 재시작 후보는 build 실패 이후 up 실행과 성공 종료를 mock으로 재현했고, 퀀트 두 후보는 메모리 fixture로 재현했다. 운영에서 실제 같은 계산 결함이 발생했다는 의미는 아니다.

전송 안내(G06a)와 대비(G06b)는 작은 독립 수정으로 앞당길 수 있다. 화면 배치·모바일 차트는 정확성·상태 표시 개선 이후 진행한다. 조합 설정(G08c)은 수집 범위(G08a)에 의존하지 않는다. 구체적인 추천 순서·선행 조건·완료 판정은 작업 색인과 역할 문서에서 확인한다.

## 검증과 진행 원칙

- 다섯 역할의 검토를 완료하고 QA의 세 공백을 완료 조건에 반영했다. 구현도 기존 역할별 세션을 하나씩 실행한다.
- 구현을 시작하면 실패 사례를 작은 임시 데이터로 재현하고, 변경 동작의 회귀를 확인한 후 관련 테스트를 실행한다.
- PostgreSQL과 SQLite 정렬·날짜 계약 차이는 실제 해당 DB 검증 여부를 구분한다. 기존 [PostgreSQL 테스트](../../tests/integration/test_postgresql_migrations.py)는 migration 검증이므로 새 repository 회귀와 CI 선택을 연결한다. 기본 테스트 통과를 운영 DB 통과로 보고하지 않는다.
- 화면 변경은 조회 전용 검증에서 데스크톱·390px·검색/선택·탭 이동·빈 상태·오래된 데이터 상태를 확인한다. [기존 AppTest](../../tests/test_streamlit_dashboard.py)와 [차트 fixture](../../tests/test_dashboard_snapshot_frame_loader.py)의 부분 mock을 통과한 것만으로 실제 renderer와 summary 연결 검증을 대신하지 않는다.
- SELECT 측정 구간을 구분한다. 과거 관심종목 네 개의 전체 rerun 3회는 당시 측정값이며, [조회 회귀](../../tests/test_watchlist_snapshot_queries.py)는 snapshot 생성 후 추가0회를 검사한다. 변경 전후 동일 fixture로 두 구간을 각각 비교한다.
- 검증 기록에 대상 HEAD·원본 경로·DB 종류·메모리 fixture/mock/AppTest/실제 브라우저 여부를 명시한다. 역할별 과거 worktree 증거와 혼합하지 않는다.
- 완료 조건을 충족한 작은 단위만 검토하고 다음 단계로 이동한다. 커밋·배포는 별도 사용자 요청을 따른다.

## 위험과 남은 확인

- 잘못된 안내의 원인을 디자인 검토만으로 확정하면 저장 계약을 손상시킬 수 있다. 원본 데이터·조회 코드·회귀 근거를 먼저 대조한다.
- 디자인 개편으로 기준일·경고·실행 결과가 숨겨질 수 있다. 압축하되 중요한 상태는 선택 대상과 함께 노출한다.
- 역할별 과거 worktree의 변경을 현재 코드로 오인할 수 있다. 현재 main을 읽고 새 변경을 기존 결과와 섞지 않는다.
- 이번 결과는 우선순위·실행 계획과 역할별 검토다. 기능 구현·재배포는 수행하지 않았으며 계획 상태는 proposed로 유지한다. 재현된 fixture 결함과 운영에서 직접 확인한 정렬 문제를 구분한다. 이후 현재 작업 상태는 역할 문서에서 확인한다.
