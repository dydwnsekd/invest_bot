02 / QUICK START

처음 실행하기

이미 설정을 마쳤다면 실행 명령부터 확인하세요. 명령은 README.md와 start.sh가 있는 프로젝트 최상위 폴더 기준이며, 아래의 예시는 설명용입니다. 이 안내서를 열거나 복사 버튼을 눌러도 명령은 실행되지 않습니다.

일상적으로 쓰는 세 가지 명령

./start.sh 시작
./restart.sh 변경 후 다시 시작
./stop.sh 전체 정지

start/restart는 이미지 빌드·설정 검사 후 DB, migration, web, scheduler 준비 상태를 확인합니다. stop은 컨테이너와 저장 데이터를 남겨 둡니다.

실행 후 접속

브라우저 주소창에 http://127.0.0.1:8000을 입력합니다.

위 주소는 기본 포트 기준입니다. INVEST_BOT_DASHBOARD_PORT를 변경했다면 그 포트를 사용하세요. 스크립트의 내부 준비 확인과 실제 브라우저 접속은 구분합니다.

시작하면 스케줄러도 함께 실행됩니다

예시 설정의 run_on_startup: true는 시작 시 수집을 수행합니다. 화면에서 버튼을 누르지 않아도 이 별도 수집 과정이 API에 접근할 수 있습니다. 사용 전 수집 주기와 시작 옵션을 확인하세요.

처음 설치하는 경우: 환경과 설정 준비

Docker와 Compose를 준비하고 Python 3.13 환경을 만듭니다. 프로젝트 Python 명령은 .venv를 사용합니다. start/restart 준비 확인기에는 POSIX Python 3.10 이상이 필요합니다.

macOS / Linux · 최초 준비
python3.13 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt -r requirements-dev.txt
cp -n config/app.yaml.example config/app.yaml
cp -n config/collection_schedule.yaml.example config/collection_schedule.yaml
cp -n .env.example .env

cp -n은 기존 파일을 덮어쓰지 않는 복사 예시입니다. 생성한 설정에 DB와 KIS 키를 채우세요. 같은 설정의 환경변수는 app.yaml 값보다 우선합니다. 키는 이 HTML에 입력하거나 저장하지 않습니다.

Windows에서는 python -m venv .venv 후 .venv\Scripts\Activate.ps1로 활성화합니다. 루트의 .sh 스크립트는 POSIX 셸 기준입니다.

Docker 대신 Python으로 대시보드 실행

기존 DB에 연결할 설정이 필요합니다. DB schema만 준비하려면 migrate-only를 명시합니다. 전체 초기화인 full은 외부 종목 마스터 작업까지 포함하므로 목적에 맞게 선택합니다.

Python 직접 실행
.venv/bin/python scripts/init_db.py --mode migrate-only
.venv/bin/python scripts/run_streamlit_dashboard.py

이 경로는 별도 scheduler를 자동 시작하지 않습니다. DB 자체는 별도로 실행돼 있어야 합니다.

03 / EVERYDAY WORKFLOW

매일은 이 순서로 사용하세요

  1. 홈에서 기준일과 데이터 상태를 봅니다.

    최신 리포트 날짜와 원본 날짜가 언제인지 확인합니다. 홈을 읽는 것만으로 새 수집이 시작되지는 않습니다.

  2. 필요한 종목만 데이터 갱신에서 준비합니다.

    종목과 기간을 선택하고 실행할 단계를 확인합니다. 수집만 필요한지, 지표·신호·리포트까지 필요한지 고릅니다.

  3. 투자 리포트에서 의견과 이유를 함께 읽습니다.

    종합 판단, 전략 합의도, 상승 근거·위험 요인·재평가 기준, 입력 데이터 날짜를 확인합니다. 미관측 값과 실제 0을 구분합니다.

  4. 관심종목으로 저장하고, 백테스트로 검증합니다.

    관심종목에서 다시 확인하고, 백테스트에서 준비 확인 → 필요 시 준비 실행 → 실행 → 결과·거래 내역을 살펴봅니다.

단순 조회

홈·리포트·차트는 저장된 자료를 읽습니다. 새 데이터가 필요하면 갱신 동작을 명시적으로 실행합니다.

데이터를 바꾸는 실행

수집·분석·신호·리포트 버튼과 백테스트 준비 실행은 결과를 만들거나 저장합니다. 전체 파이프라인/배치 리포트는 설정에 따라 Discord 전송도 시도할 수 있습니다.

투자 리포트의 검색·즐겨찾기·정렬·종목 선택은 해석 모아보기 내용보다 먼저 표시합니다. 관심종목의 검색·정렬은 상세 선택 목록에 적용되며, 아래 전체 종목판은 모든 등록 종목을 보여 줍니다. 다른 종목 카드를 누르면 검색어를 지우고 그 종목 상세로 이동합니다.

백테스트의 정적인 전략 검증 흐름은 필요할 때 펼칩니다. 준비 사유·입력 날짜·실행/저장 범위는 계속 표시되고 작은 화면의 준비/결과 카드는 한 열로 읽습니다.

차트는 창 크기에 맞춰 자동으로 조정됩니다

범례는 차트 아래에 표시되고 좁은 화면에서 자동으로 줄바꿈됩니다. 별도 모바일 모드를 고르지 않아도 됩니다. 범례 항목을 눌러 선을 숨기거나 다시 켤 수 있고 위쪽 도구 모음에서 확대·이동·축 초기화·전체 화면을 사용합니다.

크기를 바꾸는 동작은 새 수집이나 백테스트 실행을 시작하지 않습니다. 날짜·데이터 누락 안내는 차트 위에서 함께 확인합니다.

05 / DATA

수집 성공과 분석 준비는 다릅니다

최근 G08a에서 긴 요청이 한 번의 응답으로 잘리는 문제를 보완했습니다. 일반 일봉은 100달력일 이하의 겹치지 않는 구간으로 나눠 조회합니다.

요청한 범위

예: 최근 365일. 달력일 기준이며 365개의 일봉이 있다는 뜻은 아닙니다.

실제로 관측한 범위

수집된 첫날·마지막 날, 고유 일봉 수, 요청 횟수와 범위가 짧은 이유를 남깁니다.

후속 분석 가능 여부

유효한 짧은 자료는 저장합니다. 일반 분석은 최소 60개 일봉을 요구하고 관심종목 갱신은 누적 이력을 봅니다.

“구간 조회 완료”가 “모든 거래일 검증 완료”는 아닙니다

기본 거래일 캘린더는 설치돼 있지 않습니다. 휴장·신규 상장 근거가 없으면 이유를 확정하지 않습니다. 주말 경계나 유효한 짧은 자료만으로 실패시키지 않되, 페이지 오류·잘못된 가격·상충 중복은 완료로 저장하지 않습니다.

snapshot이란? 원본이나 가공 데이터 표를 저장한 결과입니다. 데이터셋과 파일명으로 식별하며 기본 저장소는 DB입니다. 정규화된 개별 행 저장은 선택적 쓰기 경로여서 모든 산출물이 같은 테이블 구조로 통일된 것은 아닙니다.

CLI에서 수집·분석·리포트 실행

아래는 단계별 명령입니다. 첫 명령은 실제 KIS 수집을 실행합니다. 후속 명령은 앞 단계의 저장 결과가 준비된 경우에 사용합니다. 단건 리포트 CLI는 기본적으로 Discord를 보내지 않습니다.

종목코드 예시 · 삼성전자 / SK하이닉스
.venv/bin/python scripts/run_collection.py 005930 000660 --days 365
.venv/bin/python scripts/run_daily_analysis.py 005930
.venv/bin/python scripts/run_golden_cross_signals.py 005930
.venv/bin/python scripts/run_market_report.py 005930

종목 파일은 --symbols-file symbols.txt로 지정합니다. 파일에는 한 줄에 한 종목코드를 적습니다.

시작·종료일을 지정해 과거 가격·수급을 보충하려면

일반 수집과 별도인 명시적 기간 CLI입니다. 가격·수급을 반복 조회해 별도 history snapshot과 지표·신호·리포트를 만듭니다. 예시 날짜는 고정된 설명값이며 필요에 맞게 바꾸세요.

과거 기간 보충 · 실제 API 사용
.venv/bin/python scripts/run_historical_collection.py 005930 000660 --start 2024-11-01 --end 2026-11-02

종목을 생략하면 저장된 시장 리포트의 종목을 사용합니다. 종료일이 오늘이면 수급은 전날까지 요청합니다. 이 CLI의 초기 구간 검증·재시도 규칙은 일반 수집과 다르며 신규 상장 등은 별도 제약이 있습니다. 기존 짧은 원본은 남깁니다.

실행 결과는 당시 선택과 입력 범위를 기억하므로 이후 기간을 바꿔도 과거 결과는 바뀌지 않습니다. 구형 이력은 기록 없음, 자료 부족·중복·불완전한 기록은 사유와 확인 불가로 표시합니다. 입력 범위 안내만으로 자동 저장하지 않으며, 결과를 보관하려면 아래 명시 저장 절차를 따릅니다.

어떤 설정을 읽나요?

config/app.yaml과 INVEST_BOT_* 환경변수입니다. 환경변수가 우선합니다. KIS mock/live 키를 분리하며, 기존 config/kis_credentials.yaml은 현재 실행 경로에서 읽지 않습니다.

토큰은 파일 캐시로 재사용해 반복 발급을 줄입니다. 캐시는 연결 성공이나 영구 유효를 보증하지 않습니다.

Git으로 관리하는 것은?

소스·테스트·설정 예시·문서를 관리합니다. 실제 키/설정·토큰·로컬 DB·로그·이미지·백테스트와 생성 리포트 등 data/ 산출물은 제외 규칙을 사용합니다.

이미 추적된 파일과 과거 커밋은 ignore만 추가해도 사라지지 않습니다. 커밋·push는 명시적 요청 후 진행합니다.

준비 확인기의 기본 한도는 서비스 전환·확인 180초, scheduler 안정 관찰 10초입니다. 빌드·사전검사 시간은 별도입니다. 실패 후 자동 롤백은 하지 않으므로 출력된 단계와 로그를 확인합니다.

11 / FAQ

헷갈리기 쉬운 질문

수집은 성공했는데 왜 리포트가 생기지 않나요?

수집 성공은 자료를 확보·저장했다는 뜻입니다. 일반 분석 기준인 유효 일봉 60개가 부족하면 후속 분석은 보류됩니다. 새로 상장한 종목은 짧은 정상 이력일 수 있습니다. 실제 관측 범위·분석 준비 사유를 확인하고, 근거 없이 휴장이나 신규 상장으로 단정하지 않습니다.

관심종목의 하루치 갱신도 60개를 새로 받아야 하나요?

아닙니다. 기존 저장분과 새로 수집한 자료를 합친 누적 유효 날짜를 봅니다. 이미 충분한 이력이 있으면 1일 추가분으로도 분석할 수 있습니다. 원본이 최신이고 리포트만 오래됐다면 수집 없이 분석·리포트만 다시 만들 수 있습니다.

시작은 성공했는데 화면이나 데이터가 준비되지 않을 수 있나요?

준비 확인은 DB health·migration·web 내부 HTTP·scheduler의 안정 상태를 확인합니다. 호스트 포트 접속, 모든 종목 데이터와 리포트 준비까지 보장하지는 않습니다. 브라우저 주소·포트·로그와 데이터 준비 상태를 따로 확인합니다.

리포트 날짜가 수집일보다 이전인 이유는 무엇인가요?

리포트는 지표·신호·수급의 공통 기준일을 사용합니다. 수급이 늦게 도착하면 그보다 뒤의 가격이 있어도 판단 날짜가 앞설 수 있습니다. 실제 원본 날짜와 리포트의 입력 날짜를 함께 봅니다.

창을 닫거나 화면을 보지 않아도 수집하나요?

브라우저와 scheduler는 별도입니다. scheduler 프로세스/컨테이너가 실행 중이면 설정된 간격과 시작 옵션에 따라 동작할 수 있습니다. interval_minutes는 컴퓨터를 깨우는 기능이 아니며, 이 프로젝트에서 OS 예약 실행을 새로 설정한 것은 아닙니다.

화면 설정 저장과 조합 전략의 영구 저장은 같나요?

다릅니다. 현재 브라우저 세션의 화면 설정 복원과 저장된 백테스트 결과 이력은 구현돼 있습니다. G08c에서는 실행 결과 저장 버튼으로 조합의 당시 설정·출처를 결과와 함께 남기고 이력에서 다시 읽습니다. 현재 화면의 입력 양식 복원과는 별개이며 저장/호환 한계를 함께 확인합니다.

수익률·승률·최대 낙폭은 어떻게 읽나요?

총수익률은 처음 자산 대비 최종 변화, 승률은 전체 거래 중 이긴 거래의 비율입니다. 최대 낙폭(MDD)은 평가금액이 이전 고점에서 가장 많이 내려간 폭입니다. 승률만 높아도 손익 규모에 따라 총수익률은 낮을 수 있습니다. 일별 평가곡선·거래 로그·매수 후 보유 기준과 함께 봅니다.

API 키나 실제 데이터가 이 안내서에 들어 있나요?

실제 설정 파일이나 토큰 내용을 가져오지 않았습니다. 설정 이름·공개 예시와 코드 동작만 설명합니다. 실제 키·DB·로그·수집/백테스트 산출물은 로컬 제외 경계를 따릅니다.

기능을 수정한 뒤 무엇을 확인하나요?

변경 범위의 테스트부터 실행하고, 필요할 때 기본 suite와 결과 XML을 갱신합니다. 아래 명령은 실제 테스트를 실행하며 시스템 검증 화면이 읽는 결과를 저장합니다.
