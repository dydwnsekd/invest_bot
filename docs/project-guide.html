01 / PURPOSE

invest_bot은 어떤 프로젝트인가요?

국내주식 데이터를 모아 지표와 전략 신호를 만들고, 과거 데이터로 전략을 시험한 뒤 대시보드에서 결과를 살펴보는 Python 프로젝트입니다.

현재의 중심

판단에 필요한 재료를 만들기

가격·수급 데이터를 수집하고 이동평균, RSI, 모멘텀 등을 계산합니다. 리포트와 차트로 결과를 읽고, 백테스트로 전략의 과거 동작을 확인합니다.

앞으로 확장할 영역

주문과 리스크 관리

모의·실거래 주문 래퍼, 중복 주문 방지, 손절·익절과 주문 전 점검은 작업 목록에 남아 있습니다. 현재 구현 범위는 연구와 검증 중심입니다.

처음 사용하는 순서

홈에서 저장된 결과 확인 → 데이터 갱신 → 투자 리포트 읽기 → 데이터 보기로 근거 확인 → 백테스트에서 전략 비교. 홈 진입 자체는 수집이나 외부 API 호출을 실행하지 않습니다.

근거: 프로젝트 README · 전체 작업 현황 · 화면 설계

백테스트 규칙 읽기 →

snapshot과 정규화 저장은 어떻게 다른가요?

snapshot은 수집·가공한 표(DataFrame)를 dataset과 파일명 단위로 보관하는 방식입니다. 주요 저장 테이블은 dataset_frames입니다.

정규화 저장은 종목·일봉·수급처럼 의미가 정해진 테이블에 행을 저장하는 방식입니다. enable_db_write 설정으로 제어하므로 두 저장 경로가 항상 함께 갱신된다고 가정하면 안 됩니다.

현재 모델에는 symbols, daily_prices, stock_info_snapshots, investor_daily, dataset_frames, report_favorite_symbols가 있습니다. DB 구조의 근거는 실제 모델과 문서 차이 기록을 함께 읽습니다.

요청일과 관측일을 왜 구분하나요?

예를 들어 주말 날짜로 수급을 요청해도 응답값은 이전 거래일의 값일 수 있습니다. 파일명에 들어간 요청일을 실제 관측일로 간주하면, 서로 다른 날짜의 데이터를 같은 날의 값처럼 비교하게 됩니다.

리포트는 실제 관측일과 공통 기준일을 확인합니다. 날짜 없는 상세 수급은 대응하는 summary의 정보로 연결하며, 관측일을 확정할 수 없는 입력은 명시적으로 거부합니다.

04 / KNOWLEDGE MAP

OKF는 문서를 읽고 관리하는 규칙입니다

이 저장소에서 직접 정의한 이름입니다. 특정 외부 표준이나 약어의 정식 확장명을 전제하지 않습니다. 문서가 무엇을 설명하는지, 현재도 유효한지, 어떤 코드가 근거인지 연결합니다.

지식 홈 · 어디로 갈까?→등록부 · 어떤 문서일까?→개념·담당 문서 · 무슨 뜻일까?→코드·테스트 · 근거는?

문서 종류 = 맡은 역할

도서관의 서가처럼 문서의 용도를 구분합니다.

  • 규칙(policy) · 작업과 갱신 원칙
  • 개념(concept) · 용어와 관계
  • 설명(reference) · 기능·인터페이스
  • 실행 안내(runbook) · 실행·확인 방법
  • 결정(decision) · 선택한 이유
  • 계획(plan) · 앞으로 할 일
  • 현황(status) · 완료·대기 상태
  • 증거(evidence) · 특정 시점의 검증
  • 색인(index) · 찾아가는 입구

문서 상태 = 지금 읽는 방법

종류가 같아도 상태에 따라 해석이 달라집니다.

active · 현재 진입점
해당 주제를 확인하는 기준 문서입니다. 모든 내용의 정확성을 자동 보증하지는 않습니다.

proposed · 제안
목표나 후보 정책입니다. 구현 완료로 읽지 않습니다.

historical · 과거 기록
당시의 결과·계획입니다. 옛 미완료 항목을 현재 작업으로 다시 실행하지 않습니다.

review-required · 재검토
알려진 차이나 미검증 내용이 있습니다. 연결된 코드와 현재 문서를 먼저 봅니다.

예: “DB schema 문서가 있으니 현재 DB와 똑같겠지?”

등록부를 보면 종류는 reference, 상태는 review-required입니다. 예전 ERD에는 관심종목 테이블이 빠져 있고 종목 쓰기 정책에도 차이가 있습니다. 개념 지도에서 차이를 읽고 실제 모델·마이그레이션을 확인하면 됩니다.

ID와 관계는 왜 필요한가요?

D-BACKTEST는 백테스트 현황 문서의 ID이고, K-EQUITY는 일별 평가금액 개념의 ID입니다. 문서 ID는 경로가 바뀌어도 유지하도록 정했습니다.

관계는 “누가 무엇을 만든다(produces)”, “무엇을 사용한다(consumes)”, “무엇을 설명한다(describes)”, “무엇으로 검증한다(verified-by)”, “어떤 문서로 대체됐다(superseded-by)”를 나타냅니다.

예: 수집 → snapshot 생성 / 백테스트 → 전략 사용 / 평가금액 개념 → runner 코드 설명·관련 테스트로 검증. 별도 그래프 DB 없이 Markdown의 표와 링크로 관리합니다.

05 / HOW TO READ

궁금한 것에서 시작하세요

문서 전체를 순서대로 읽을 필요는 없습니다. 질문에 맞는 진입점을 선택하고 필요한 근거만 따라갑니다.

“어디까지 개발됐지?”

task 요약 → 해당 기능 task → 개선 작업 추적

날짜별 기록과 최신 상태를 구분합니다. 옛 전략 후보 목록의 체크박스는 현재 구현 상태를 대신하지 않습니다.

“이 리포트 숫자는 무슨 뜻이지?”

리포트 가이드 → K-ASOF 개념 → 생성 코드와 기준일 테스트

요청일·관측일·공통 기준일이 같은지 먼저 확인합니다.

“이 설계는 왜 이렇게 했지?”

결정 기록 → 관련 설계·담당 문서 → 코드

결정 기록이 아직 없는 판단은 문서에 없다고 구분합니다. 이번에 새로 기록한 결정은 OKF 도입입니다.

“수정 후 무엇을 남기지?”

담당 문서 갱신 → 코드·검증 근거 연결 → task 상태 갱신 → 새 문서는 등록부에 추가

작성 양식을 사용합니다. 과거 테스트 결과는 날짜와 함께 보존하고 새 검증을 구분합니다.
